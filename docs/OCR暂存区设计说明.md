# OCR 暂存区设计说明 (V0.6)

## 1. 为什么不直接把 OCR 结果写入 raw_inputs

OCR（光学字符识别）结果通常包含：
- 识别错误（错别字、漏字）
- 排版混乱（多行合并、断句错误）
- 无关信息（系统状态栏、聊天头像等）

如果直接写入 `raw_inputs`，会产生以下副作用：
1. **污染原始池**：导致 `raw_inputs` 充斥大量垃圾数据，难以回溯。
2. **解析压力**：解析引擎会尝试处理这些低质量文本，产生大量误报或低质量的 `parsed_records`。
3. **确认负担**：用户在“人工确认”环节需要处理更多由于 OCR 错误导致的异常记录。

因此，引入 **OCR 暂存区** 作为入口缓冲区。

## 2. OCR 暂存区的作用

- **隔离**：将不确定的 OCR 结果与核心工作流隔离。
- **初审**：提供一个简单的界面供用户在数据进入主流程前进行快速预览和修正。
- **过滤**：用户可以丢弃无效的 OCR 结果（标记为 ignored），不浪费后续解析资源。

## 3. 当前 V0.5 支持范围

- **手动粘贴**：用户可以手动将外部 OCR 工具识别的文本粘贴到暂存区。
- **记录管理**：支持暂存记录的列表显示、状态过滤、详情查看。
- **人工修正**：支持在界面上对原始 OCR 文本进行编辑（cleaned_text）。
- **流程导入**：确认无误后，点击“确认导入”才会正式写入 `raw_inputs`。

## 4. 后续接入微信长图识别的边界

- **解耦设计**：未来接入 `pytesseract` 或 `PaddleOCR` 时，识别结果将直接通过 `OCRStagingService` 创建 `draft` 状态的暂存记录。
- **异步处理**：长图识别可以异步进行，识别完成后用户在暂存区批量审核。

## 5. 数据流转说明

1. **录入层**：截图/图片/OCR结果文本。
2. **缓冲层**：`ocr_staging_records` (SQLite) 暂存。
3. **人工层**：用户查看、修正 `cleaned_text`、点击确认。
4. **主流程层**：写入 `raw_inputs` -> 自动触发智能解析 -> `parsed_records` -> 人工确认 -> 导出。

## 6. 安全边界

- **不可逆操作**：一旦记录标记为 `imported`，则不可再次修改暂存内容，确保数据流向的一致性。
- **不自动合并**：暂存区不尝试自动合并多条记录，保持数据的原子性。
- **不自动解析**：暂存记录在导入 `raw_inputs` 之前，不参与任何业务逻辑解析。

## 7. 人工确认要求

- 用户应至少检查核心字段（如日期、人员名、项目名）在 OCR 文本中是否识别正确。
- 对于微信聊天长图，建议删除无关的聊天记录，只保留工作日报相关的文本。

## 8. 下一步 OCR 识别前准备事项

- 评估 OCR 引擎的选择（PaddleOCR 离线性能较好）。
- 准备图片预处理逻辑（灰度化、去噪、长图切割）。
- 建立 OCR 识别准确率的测试集。

## 9. V0.6 OCR Lab 验证框架

在 V0.6 阶段，我们引入了 `tools/ocr_lab/` 目录，其定位为：
- **独立验证**：不作为主程序的依赖，仅用于开发环境下验证 OCR 引擎。
- **模拟入口**：通过 `ocr_probe.py` 脚本，允许使用现有文本模拟 OCR 识别结果并直接写入暂存区。
- **解耦设计**：未来任何 OCR 引擎的接入都将通过此框架进行预验证，确保主程序的稳定性。
- **人工审核**：识别结果进入暂存区后，必须遵循现有的“人工审核-修正-导入”流程，严禁绕过人工直接进入主库。
