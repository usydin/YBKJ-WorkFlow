# OCR 技术选型说明

## 1. 本项目 OCR 的实际目标

本项目引入 OCR 的核心目标是提升数据录入效率，具体包括：
- **主要识别对象**：微信群中维修记录的长图、截图。
- **数据流转**：识别结果不直接进入核心业务库，而是进入 **OCR 暂存区**。
- **人工干预**：用户在暂存区人工修正后再导入 `raw_inputs`。
- **定位**：OCR 仅作为输入辅助工具，不直接生成日报，不参与最终业务逻辑的自动执行。

## 2. 候选方案分析

### A. PaddleOCR (推荐作为未来可选模块)
- **优点**：中文识别能力极强，支持长图识别，社区活跃。
- **缺点**：依赖重（PaddlePaddle），打包体积大（数百 MB），环境配置相对复杂。
- **结论**：适合作为后续独立 OCR 工具或可选模块，不建议作为主程序硬依赖。

### B. Tesseract
- **优点**：开源成熟，轻量级，支持多平台。
- **缺点**：中文识别效果高度依赖语言包，对微信长图这种复杂排版和混合字体的识别率未必理想。
- **结论**：需要外部可执行文件支持，适合简单场景。

### C. macOS Vision / Apple OCR
- **优点**：macOS 系统原生支持，识别率高，无需额外依赖。
- **缺点**：不跨平台，无法支持 Windows 绿色版交付。
- **结论**：可作为开发环境下的预处理方案，不作为通用路线。

### D. 系统级 OCR 辅助 (Windows OCR / PowerToys)
- **优点**：最轻量、最安全，无需本项目集成任何代码。
- **缺点**：需要人工手动操作（截图 -> 复制文本 -> 粘贴）。
- **结论**：作为第一阶段落地的主要路线。

### E. 手动复制/第三方 OCR 后粘贴
- **优点**：最稳定，无任何开发成本。
- **结论**：V0.5 已完全支持此流程。

## 3. 推荐演进路线

1. **第一阶段 (当前)**：手动 OCR / 外部工具 -> 粘贴到 OCR 暂存区。
2. **第二阶段 (V0.6)**：建立 `tools/ocr_lab/` 独立验证框架，编写 `ocr_probe.py` 脚本测试不同引擎。
3. **第三阶段**：若 PaddleOCR 或其他本地引擎识别质量稳定，开发为“可选模块”。
4. **第四阶段**：在 GUI 中增加 OCR 入口，但主程序启动不应依赖 OCR 引擎。

## 4. 安全边界与风险管理

- **隐私保护**：不自动上传任何截图到第三方 API，坚持本地化识别。
- **数据留痕**：暂存区保留原始识别文本（raw_text）以便回溯。
- **打包风险**：OCR 依赖会显著增加 EXE 体积，需单独验证绿色版迁移的兼容性。
- **敏感信息**：`dataset/samples/screenshots_raw/` 目录严禁提交包含真实姓名、电话、门牌号等敏感信息的截图。

## 5. 打包建议

由于 OCR 依赖较大，建议后续打包时：
- 提供“轻量版”（无 OCR 引擎）。
- 提供“增强版”（内置 PaddleOCR 或其他引擎）。
